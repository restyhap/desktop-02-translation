### 一、 快捷键设计思路

GoldenDict 等早期软件体验不好的根本原因在于它们使用了 **“拦截-等待-模拟”** 的粗暴机制：

1. 按下 `Ctrl+C`，软件**拦截**该事件（系统此时没复制）。
2. 软件启动一个定时器（如 500ms）等待第二击。
3. 如果超时，软件再**模拟**发送一次 `Ctrl+C` 给系统。 **痛点**：这种机制会导致系统复制出现明显的延迟感，且在部分对键盘 Hook 敏感的软件（如游戏、某些 IDE）中会直接失效。

#### 💡 最优化的设计原则：“首击零拦截 + 时间窗口状态机”

1. **首击绝对不拦截（Zero-Interception for First Stroke）**： 当用户按下 `Ctrl+C` 时，**不要拦截**，让操作系统瞬间完成复制。我们的程序只是在后台“偷听”并记录时间戳。这保证了原生功能的丝滑。
2. **次击精准拦截（Precision Interception for Second Stroke）**： 在设定的时间窗口（如 500ms）内，如果检测到了第二击（如 `C`），此时**拦截**第二击（防止用户输入字符 'c'），并触发翻译。
3. **合理的时间窗口（Timeout）**： 人类连续按键的舒适间隔通常在 `300ms - 600ms` 之间。建议默认设置为 `400ms`，并允许用户在设置中微调。
4. **视觉/状态反馈**： 在等待第二击的 400ms 内，可以在鼠标指针旁显示一个极小的半透明图标（如一个小字典图标），提示用户“正在等待第二击”，消除等待的焦虑感。

#### Tauri 技术实现方案

Tauri 原生的 `global-shortcut` 插件只能注册单一快捷键，不支持序列和超时。因此，我们需要**绕过 Tauri 原生插件，使用 Rust 底层库进行全局键盘监听**。

- **全局键盘监听**：使用 Rust 的 `rdev` 库（跨平台全局键盘/鼠标 Hook）。
- **异步与定时**：使用 `tokio` 处理超时逻辑。
- **前后端通信**：使用 Tauri 的 `emit` 事件机制。
